# 对话补参与执行状态机

仅在根路由选出唯一角色后加载本文件。操作细节以该角色的 `operations.md` 为准。

## 状态

`意图识别 → 角色路由 → 身份校验 → 参数收集 → 范围校验 → dry-run → 写入确认 → 高危计划 → 单次执行 → 最小结果`

以下任一情况立即停止：角色歧义、`activeRole` 不符、对象或范围不唯一、401/403、计划失效、用户否认、写请求结果未知。

## 补参规则

1. 从角色操作索引找到唯一 `operationId`；找不到或命中多个时只澄清动作，不调用接口。
2. 对照 `必填输入`。一次集中询问缺少的必要参数，并说明用途；可选参数采用索引声明的默认值，未声明默认值不得猜。
3. 姓名、手机号、客户名不能替代后端 ID。只有当前对话已经唯一绑定对象 ID 时才可沿用；禁止用列表接口枚举、猜测或模糊匹配目标。
4. 身份、角色、公司、部门、客户、流程、文档、用户、产品、分页范围、文件、MIME、覆盖均不得自动推断。
5. 创建任何内部用户都必须先得到明确的 `companyId` 与 `departmentId`，并确认该部门属于该公司；缺任一项都停止补问，不得仅凭公司名或部门名猜ID。`companyId`只用于对话范围和归属校验，最终 `UserRequest` JSON 不包含该字段。示例：“创建 P9，手机号和姓名已给出”仍缺两个ID；P9 的 `managerUserId` 必须为空。

## 审计 reason

- 选出唯一 `operationId` 后，Agent 必须确定性生成 `--reason internal-test:<operationId>`，例如 `internal-test:admin.user.create-p9`。
- reason 是内部CLI审计字段，不是业务参数。不得向用户索要 `--reason`、测试原因或工单号，也不得让用户选择或改写。
- reason 只能包含固定前缀和操作索引中的 `operationId`；禁止包含姓名、手机号、对象名称、自由文本、凭据或其他用户输入。
- 同一次操作的 dry-run 与正式执行必须使用完全相同的 reason；若 `operationId` 变化，废弃原计划并重新 dry-run。

## 写入确认

- dry-run 只展示：角色、`operationId`、对象 ID、动作、影响、文件数量/大小及脱敏字段，不展示请求体、凭据、完整手机号或绝对路径。
- 询问：“是否以 `<角色>` 对 `<对象ID>` 执行 `<动作>`，影响为 `<影响>`？”
- 只有紧邻 dry-run、绑定未变化的当前回合明确肯定才有效。任何参数、对象、文件、确定性 reason 或 Profile 变化都重新 dry-run。
- R3/R4 操作还必须使用五分钟单次 `plan-id`；失败、过期或变化后重新生成。

## 结果未知

写请求发生 `TIMEOUT` 或 `NETWORK_ERROR` 时进入 `OUTCOME_UNKNOWN`：不得重放原请求。先按操作索引的 `写后校验` 执行精确只读查询或查审计；无法确认时报告“结果未知，需人工核对”。
